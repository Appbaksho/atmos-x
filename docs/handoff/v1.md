## 1. What works, end to end

Atmos X is a FastAPI + Postgres/PostGIS API with a job worker (`apps/api`) and a Next.js 16 web app and PWA (`apps/web`) that reaches the API only through `/api/v1` rewrites. No language model and no Google Earth Engine are used anywhere.

```bash
cp .env.example .env          # the core heat loop needs no third-party keys
make env                      # web-only variables → apps/web/.env.local
cd apps/web && npm ci && cd ../..
make dev                      # Postgres :5433, migrations, reference data, API :8000, worker, web :3000
```

Open `/` for the landing page or `/app?demo=1` for the Dhaka demo. First admin: `cd apps/api && uv run python -m app.scripts.make_admin you@example.org`.

**Verified on a clean database (Stage 7 exit):** migrations and seed ran; the API answered a cold Dhaka scan with honest "no data" hexes in 0.7 s; the worker then computed the region in about 4 minutes; after that `/zones` returned satellite-labelled hexes with Landsat acquisition dates (2 Nov 2026) in 0.23 s.

**Main flows (all exercised by Playwright, Chromium):**
- **Heat and planning:**
  - The satellite Heat Score on a hex map (200 m · 500 m · 1 km).
  - Zone detail with driver shares.
  - Goals, feasibility, a plan with costs, species and planting spots, and the projection.
- **Location:** there is no silent default place. The app resolves the place from the device, a chosen place, the city from the IP address, or the labelled demo; otherwise it asks.
- **Acting and points:**
  - Log an action with a photo; deterministic checks; verification.
  - My trees with check-ins every 15 days, cooling estimates, and sharing a tree as a post.
  - A points ledger where points are pending until a tree's 90-day check-in.
- **Community:** teams of 2–5, invites, chat, a feed with mentions and moderation, events with GPS check-in, sponsor logos and certificates, leaderboards, and org CSV exports.
- **Store and marketplace:**
  - Points store: redeem for a 14-day voucher and QR, with monthly limits.
  - Saplings from nurseries, paid through SSLCommerz (sandbox).
  - Partner portal: products within the price band, pickup outlets, voucher collection, and an impact report PDF.
  - Company account:
    - Registration with private documents and an admin review.
    - Packages, with tree CO₂ always labelled "estimate, not an offset".
    - Money held until each tree is verified, with a recorded fee per tree.
    - Credit lots that can't be sold without certification.
    - Invoices and certificates as PDFs.
  - Admin screens.
- **Alerts and help:**
  - Farmer alerts from 10 rules on NASA and weather data.
  - Air quality: measured OpenAQ stations next to labelled models.
  - Ask Atmos: rule-based answers from the app's own data in 10 languages, under 2 s.
  - Heat-warning notifications.
  - Web push, which is off until VAPID keys exist.
- **The app:**
  - Landing page with live NASA sources, a sitemap, robots and hreflang.
  - An About page built from `/sources`.
  - 10 languages with RTL and dark mode, at 360 and 1280 px.
  - An offline app shell on production builds.

**Deployed 8 Nov 2026 at https://atmosx.baksho.app** (owner's request, after this report was first written) on the shared VPS with `docker-compose.prod.yml` (db, api, worker, web, each CPU- and memory-capped) behind the existing nginx and certificate; steps and rollback in `docs/deploy.md`. On the fresh production database a cold Dhaka scan answered in 0.77 s and the region had Landsat-labelled hexes (2 Nov 2026 scenes) about 2 minutes later; warm scans take 0.16 s.

## 8. Where the prompt was wrong or optimistic

- **D15:** GEOS-FP `tavg1_2d_slv_Nx` has no `t2mdew`. Feels-like uses Open-Meteo humidity instead.
- **D16:** plain OLS on land-cover shares gave sealed ground a cooling effect on real Dhaka data, because the shares sum to about 1. The fit is now sign-constrained with a small ridge (R² 0.42 on 15,990 hexes).
- **D17:** IMERG through GES DISC OPeNDAP needs a URS cookie and rejects bearer tokens. Daily files are read by a worker job instead.
- **D18:** with the §7.1 cap of 4 concurrent reads, a cold Dhaka region takes about 1–2 minutes, not the 30 s target. Scans return partial results in under 2 s meanwhile.
- **D12:** `earthaccess` was not needed; a few direct HTTP calls cover the token and reads.
- **E3 wording:** "no third-party call in any request path" conflicts with place search and reverse geocoding, which are proxies to a geocoder by nature. Those endpoints stay live; everything else reads caches or queues jobs.
- **Process:** the prompt said to commit on one `v1` branch. The owner asked for a branch per topic, merged through PRs (D1).
